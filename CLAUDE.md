# CardSelector

Personal phone page for searching credit card merchant bonuses: type part of a merchant name ("amaz"), see which cards offer a bonus there, tap a result for full details. Static site (plain HTML/JS, no build step) on public GitHub Pages.

## Data
- `site/data/offers.json` = `{ "categories": [...], "batches": [...], "offers": [...] }`. It is large (100+ records): read only its first few records unless you need more; use `grep`/`python3` for lookups.
- **`OFFER_RECORD.md` is the source of truth** for fields and rules; follow it exactly. Summary:
  - Offer fields: `id` (`card-slug/merchant-slug`, the match key), `card` (nickname only; no account numbers, the repo is public), `merchant`, `category`, `bonus`, `expires` (ISO or null), `expires_text`, `activation` (`needs_activation` | `already_activated` | `none_shown`), `channel` (`in_store` | `online` | `pay_at_pump` | `in_store_and_online` | `in_store_and_app` | `none_shown`), `spend_cap`, `minimum_spend`, `fine_print`, `other_details[]`, `last_read`, `first_seen`, `status`, `status_since`. Verbatim text; `null` when not on the screenshot, never guess.
  - **Cuisine (Dining only):** `site/data/cuisines.json`, keyed by merchant name, one cuisine per merchant from a fixed list of 21 (`OFFER_RECORD.md`, Cuisines). Untagged active Dining merchants wait on its `to_classify` list.
- **Category (every offer):** assign exactly one `category` from the fixed list (`categories` in `offers.json`, listed in `OFFER_RECORD.md`) to every new offer as it is saved, inferred from the merchant name. Same merchant = same category on every card (reuse what is already saved). If you can't tell what a merchant sells, list those merchants for the owner to correct instead of guessing silently. The validator rejects a missing/unknown category or a merchant with different categories on different cards (names compared like search: case, accents, spaces and punctuation ignored; Alibaba / Ali Baba is a named exception, two different businesses).
  - **Bonus categories:** `site/data/bonus-categories.json`, separate from offers so refreshes never touch it. Rules and the quarterly refresh are under **Bonus categories** below.
  - Status: `active` (searchable), `missing` (unexpired but absent from a newer batch), `expired`, `used` (user said so). Only `active` is searchable; `missing`/`expired` show under "Recently unavailable".
  - Cleanup: delete `expired`/`used` 30 days after `expires`, `missing` 30 days after `status_since`.
  - **`first_seen`** = the read date of the batch that first added the offer to the app. Set only when an offer is new (an id the app doesn't have); never changed after, by any refresh, rename, pairing, return from `missing`, or edit. Every refresh script must copy it from the saved offer. (All current values are 2026-10-18 because every read so far, first imports and refreshes, was dated 2026-10-18.)
  - Missing year on an expiry date: use the next upcoming occurrence.

## Adding offers (batches)
- Screenshots arrive as chat attachments. Read them and save immediately, no approval step. **Never write screenshots into the repo** (`screenshots/` is git-ignored anyway).
- New batch for a card: match on `id`; add new, update existing (set `last_read` to the batch date), a hidden offer that returns becomes `active`, a `used` offer stays `used`.
- Multi-part batches: save each part with `last_read` = batch date, but only mark offers `missing` and add the `batches` entry when the user says "batch complete". Missing = card's `active` offers with `last_read` older than the batch date.
- Chase list screenshots (method A, the first batches) show no expiry, caps, minimums or fine print (those are in the offer pop-ups), so those fields were `null`. Both Chase cards are now read by method B (live-page CSV, exact end dates), which fills them: see the Chase Freedom Flex rules below.
- **Cuisines (after every apply that touches Dining):** run `python3 tools/cuisines.py sync`. It puts every active Dining merchant with no cuisine entry on `to_classify` and reports entries whose merchant was renamed (move them with `--rename`, or rename the key in the same script that renamed the merchant; U.S. Bank and Chase renames add no alias, so alias matching won't catch them). Only the merchants on `to_classify` get classified (knowledge first, lookups only for what can't be placed); everything already tagged stays as it is, and `locked` entries are never touched. Rules in `OFFER_RECORD.md` under Cuisines.
- **Read date (every card, every batch):** the date the owner read the issuer's page, **in the owner's local time (US Pacific)**, as the owner or the file states it. Never the container clock (UTC), a commit or import time, or "today". An evening read in Pacific is already the next day in UTC: the Bank of America import (read the evening of 2026-10-18, committed 00:08 UTC on 10-19) was stamped 2026-10-19 on its batch and on every offer's `last_read`, `first_seen` and `status_since` until it was corrected. If the date isn't given, ask. Use the one date for the `batches` entry, for `last_read`, for `status_since` where the status changes, and for `first_seen` of offers new to the app only.
- Run `python3 tools/validate.py` before every commit that touches data. Refreshes of the seven cards below run through `tools/refresh.py` (**Refreshing a card**, below), not throwaway scripts.
- **Pending phone edits:** phone offer edits wait in `site/data/phone-edits.json` until the **Fold phone edits** workflow (`.github/workflows/fold-phone-edits.yml`, nightly about 3 a.m. Pacific or "Run workflow") writes them into `offers.json` on `main` and deploys (every "Run workflow" deploys, so it also repairs a failed fold deploy; the phone's save bar and "Last deploy" follow `pages.yml` only). Sessions never fold and never write that file. Rules that depend on status or activation (used stays used, phone activation kept, the size check's active count) read `offers.json` plus pending edits (`with_pending()` in `tools/fold_phone_edits.py`); the edit wins over `offers.json` for the fields it sets, so don't change those (`status`, `status_since` and the `Used on` note for a status edit; `activation` for an activation edit). Cleanup skips offers with a pending edit, and none is deleted or given a new id (a later fold and cleanup handle them). Phone edits that land mid-session merge in as usual; if merging `main` conflicts in `offers.json` (a fold landed), take `main`'s `offers.json` and re-run your change on it; never keep your side.

## Refreshing a card (`tools/refresh.py`)
- **The tool:** `python3 tools/refresh.py report --card "<card>" FILE.csv [--read-date YYYY-MM-DD] [--template decisions.json]`, then `python3 tools/refresh.py apply --card "<card>" FILE.csv --decisions decisions.json`, for Chase Freedom Flex, Chase Freedom, U.S. Bank, Capital One, Bank of America, Citi Double Cash and Citi Custom Cash. It encodes the per-card rules below and in `OFFER_RECORD.md`: one shared core (match on normalized name + normalized bonus, `&` read as `and`, aliases count; mechanical pairing; snapshot / missing / used / returning; size check; dates; cleanup; aliases and notes) and one adapter per issuer (columns, channel and activation labels, Chase end timestamps in Eastern time, Citi and U.S. Bank countdowns, badges, Citi Redeemed rows, repeat-tile and location merges). `report` changes nothing; `apply` writes `offers.json` and the `batches` entry, moves a cuisine entry when a Dining rename adds no alias (copies it when other offers still use the old name), runs `tools/cuisines.py sync` and `tools/validate.py`, and puts both data files back if either fails. Multi-part batches: `apply --part` saves each part as it arrives (no missing, size check or `batches` entry); at "batch complete" run `apply --complete-parts` on the last part: offers already read on that date by an earlier part count as in the batch and in its size, as `OFFER_RECORD.md` says (missing = active offers with `last_read` older than the batch date); or run plain `apply` on every part CSV at once. Without `--complete-parts` only the files of the run are the batch, even on a second read dated the same day; a plain apply after `--part` runs with no batch logged for that date stops (`parts`). A re-run for the same card and date replaces its `batches` entry. Only the current live-read formats are known; an older screenshot pre-read CSV is refused (its import rules stay under Per-card rules).
- **Automatic vs proposed:** exact matches, alias matches, truncated names, a name whose words start the other name with the same bonus, Capital One `merchant_tld`, Citi domain names (incl. the approved close matches and Splash), and a same-name bonus change are automatic. Anything else that looks like a pair (one name inside the other, close spelling, several candidates) is **proposed** with its reason, and apply refuses until each is decided in the decisions file (`pairs`), together with `categories` for new merchants with no saved namesake (`{"category": ..., "unsure": true}` marks an unsure one), `clashes`, and optional `new_names` (a new offer saved under a qualified name, like `HATCH (yakitori restaurant)`). `report --template` writes the file with every open question null. A pair the tool did not propose can be added the same way: before counting anything new or dropped, check the new and missing lists for naming differences (misspellings, abbreviations: Blue 70 -> blueseventy). `owner_approved` (`size_check`, `missing`, `new_share`, `card_check`, `parts`) only after the owner said go ahead.
- **Card check:** the file's own `card` column (the app nickname, added by Chrome reads from the card picked on the page) or `card_name` (the Chase Freedom file) decides: naming this card accepts, naming another card refuses. On the four sibling cards (both Chase, both Citi) a file with neither column, or with one blank on some rows, stops for the owner (`card_check`). The file name is never evidence; a list that leans to the sibling card's offers only prints a warning.
- **Read date:** a `read_date` column identical on every row is used (and shown); otherwise `--read-date` is required. Never today or the container clock. A date before the card's newest batch is refused. Expiry and the 30-day cleanup count from the read date, for the refreshed card only.
- **Ended offers:** an active offer not in the file whose `expires` is before the read date is expired by date (`status_since` = the read date; held if it has a pending phone edit), not missing, and doesn't count toward stop b; the size check compares the batch with the card's active offers not ended by the read date plus ended ones the file has again (one ending on the read date still counts and can go missing).
- **Short file after a mass expiry:** only warned about, never stopped, because ended offers are hidden either way and a re-read restores renewed ones: under 40% of the card's last full read (`offers_found` minus offers marked used since), the report prints "File is N% of the last full read (M offers). If the page looked fuller, re-read it." near the top; pass that line on in the final report.
- **Never:** card or account numbers (card detail columns such as `card`, `card_name` and `card_last4` are read only by the card check, never stored, digits in them ignored; apply refuses if any value it would write carries their digits or a 4-digit group of the file name that is not part of a real date within a month of the read date, and the report masks them); writing `phone-edits.json`, folding, changing a field a pending edit sets, or cleaning up an offer with a pending edit; committing an issuer CSV (`.gitignore` keeps `*.csv` out; the only CSVs in the repo are the test fixtures in `tools/fixtures/`, with no card numbers).
- **Choices where the rules were silent** (tell the owner if one should change): count notes (`N tiles listed`, `N locations listed`) follow the current read, dropped at one; other badge / tag notes are only added, never removed (Chase `Tagged New` follows the file); a new Chase offer gets `needs_activation`; a pair that is not a truncated name takes the file's name with the old name in `aliases` (except a Chase banner name and a bare lowercase domain, and a cut-off name in the file never replaces a full saved one); an accepted pair whose file name is a bare lowercase domain keeps the saved name and gets the domain as an alias, so the next read matches it; a different bonus at a merchant whose saved offer is `used` is proposed, not an automatic bonus change; Chase `expiration_text` that does not mention expiry is kept but flagged; Bank of America rows of one offer with badges other than the Life Extension pair keep the strongest (`needs_activation` > `via_shop_link` > `already_activated` > `auto_enrolled`) and are flagged; Citi `promo_tag` `New` is not stored; only `<base> - <location>` names on Citi `RN-` rows are split (`Nick The Greek Woodland Hills` stays whole).
- **Tests:** `python3 tools/refresh_test.py` (fixtures in `tools/fixtures/`, a 42-offer snapshot of `offers.json` and one CSV per issuer in its real columns; runs on pull requests via `.github/workflows/sort-tests.yml`).
- **Standing procedure:** run `report`. Settle doubtful pairs (web lookups as the per-card rules say) and categories yourself under the existing rules. Then `apply`, run `python3 tools/validate.py`, open a PR, merge it, and confirm the deploy is green, without waiting for the owner. **Stop after the report and ask the owner** if any of these is true:
  a. the size check fails (batch under 70% of the prior active count);
  b. more offers would become missing than the larger of 5 or 5% of the card's prior active count;
  c. new offers are more than 25% of the batch;
  d. a pair is still doubtful after lookups;
  e. there is no read date.
  The report prints a, b and c under "Stop conditions"; apply refuses them until `owner_approved` names them.
- **Final report to the owner:** any report warning (size, card check), counts (matched, paired, bonus changes, new, missing), the list of offers that became missing, renames, new merchants with their categories (mark the unsure ones), cuisine results (entries moved, merchants put on `to_classify` and how they were classified), and the PR and deploy status.

## Per-card rules
- **Chase Freedom Flex:** every batch is a complete snapshot of the card. At "batch complete", every offer saved for this card that is not in the batch becomes `missing` (hidden from search) even with no date; `used` ones stay `used`. `missing` offers are deleted 30 days after the batch that dropped them (`status_since`); one that reappears in a later batch becomes `active` again.
  - **Read method:** Chase is now read by **method B**, a complete live-page CSV of the Offers page (columns `offer_id, merchant, bonus, reward_type, reward_amount, min_spend, reward_cap, channel, added_state, tile_cta, expiration_text, offer_end_timestamp, days_remaining, section, category, promo_text, new_badge, conditions, short_message, reward_description, tile_position, option_count, passes`), which gives **exact end dates**. Method A (screenshots of the list view, no dates) was only the first batch. The Freedom Flex and the Chase Freedom are **separate reads**: one CSV per card, never combined, each refreshed and size-checked on its own.
  - **Refresh:** `tools/refresh.py` (Chase adapter; **Refreshing a card**). Match key = normalized name + normalized bonus; a paired truncated name takes the file's full name with no alias and drops `Name truncated on screen`; a longer banner name in the file (YouTube Premium) keeps the app's name; `expires` from the end timestamp in Eastern time; `NONE` channel and `added_state` never overwrite; `Tagged New` follows `new_badge`. The single-location `reward_description` names no address, so no location note.
- **Chase Freedom** (the original Freedom Visa, not the Flex; nickname only, no account or last-four numbers): same rules as the Flex. Its list view looks the same (card grid, "+" add button, "New" / "Expiring soon" tags, no expiry dates, caps, minimums or fine print), so every batch is a complete snapshot of the card, with the same missing / `used` / 30-day cleanup handling. Ids are `chase-freedom/<merchant-slug>`. Its first batch was saved in two parts (screenshots). It is now read by **method B** like the Flex (one CSV per card, never combined with the Flex), with the same refresh procedure.
  - **Refresh:** `tools/refresh.py`, as the Flex. Its file names columns differently (`bonus_as_shown`, `end_timestamp`, `new_badge` `yes` / `no`; `dom_badge` is only the visible tag, so `new_badge` decides `Tagged New`) and carries `card_name` / `card_last4`, which are never stored (the tool also refuses a file whose `card_name` is not `Freedom`). Blank `expiration_text`, and Chase Travel's travel-timing sentence, give the date only.
- **Size check (Chase, both cards):** before marking anything missing, compare the batch's offer count with the card's `active` count from before the batch. If the batch has more than ~30% fewer offers (under 70%), warn the owner and wait for their go-ahead; do not mark missing or add the `batches` entry until they say so.
- **U.S. Bank:** one card, `card` = `U.S. Bank` only (no account or last-four numbers). It stands for the owner's two U.S. Bank cards, whose offers are shared, so there is one set of records, ids `us-bank/<merchant-slug>`. If the two cards' offers ever differ, tell the owner.
  - Rules: date-based defaults from `OFFER_RECORD.md` plus the Chase snapshot rule: every batch is a complete snapshot, so at "batch complete" every `active` U.S. Bank offer not in the batch becomes `missing` even with no date (`used` stays `used`; `missing` deleted 30 days after `status_since`; one that reappears becomes `active`). The Chase size check applies too (batch under 70% of the previous `active` count: warn and wait).
  - Batches arrive as a CSV pre-read of the screenshots (columns `card, merchant, bonus, activation, channel, days_left_badge, expires_est, page_section, name_truncated, notes, read_date`), imported with a script. `activation` and `channel` map straight to the fields; the CSV `page_section` is ignored (assign our own `category`, reusing the category a merchant already has on any card).
  - `expires` = `expires_est` (an estimate from the "N days left" tile, so a later batch can correct it); `expires_text` = the tile wording as shown ("3 days left", "Expiring today"); both null when the tile shows no days left. Spend cap, minimum and fine print are not on the screenshot list view: `null` (the live-page refresh below fills minimum and fine print).
  - Merchant names are kept as shown, including truncated ones ("Fishbone Seafood Woo..."); never guess the full name. Add `Name truncated on screen` to `other_details`. A second tile for the same merchant gets id suffix `-2` (La Colombe: in-store tile `la-colombe`, online tile `la-colombe-2`).
  - `other_details` holds on-screen text only (`Tagged New`, `Logo shows 'Subscription Only'`, `Logo shows 'Membership Only'`, `Logo shows 'In-Store Only'`, `Tile label reads 'Pay at pump only'`, `Also shown in the Featured section...`), not the reader's commentary.
  - **Marking used:** the owner says which of their two U.S. Bank cards they used. Set `status: used` and add `Used on <the card they name>` to `other_details` (nickname only, no account or last-four numbers).
  - **Refresh:** a complete live read of the cash back deals page as one CSV (`deal_id, merchant, bonus_as_shown, ..., end_date, days_left_badge, ...`), applied with `tools/refresh.py` (U.S. Bank adapter; **Refreshing a card**): match on normalized name + bonus, a paired truncated name takes the full name with no alias and keeps `Name truncated on screen`; exact `end_date` in Eastern time replaces the countdown estimate; `0.2` minimum = none; fine print from `reward_copy` only where empty; single-location deals get the `Offer only applies to the following location: ...` note. Notes written by hand (Ninja Kitchen's `Page text says: Exclusive for Smart Rewards, offer valid one time only`) are kept; the tool never writes such notes.
- **Capital One:** one card, `card` = `Capital One` only (no account or last-four numbers). It stands for the owner's two Capital One cards (Quicksilver and Discover it), whose offers are shared, so there is one set of records, ids `capital-one/<merchant-slug>`. A merchant with two tiles at different bonuses gets `-2`, `-3` (`pura`, `pura-2`). If the two cards' offers ever differ, tell the owner.
  - Rules: same as Chase (every batch is a complete snapshot; at "batch complete" every `active` Capital One offer not in the batch becomes `missing` even with no date; `used` stays `used`; `missing` deleted 30 days after `status_since`; one that reappears becomes `active`) and the same size check (batch under 70% of the previous `active` count: warn and wait; the first batch skipped it). No expiry is shown: `expires` and `expires_text` are null; `activation` is `none_shown`.
  - Batches arrive as a combined CSV pre-read (columns `card, merchant, bonus, minimum_spend, channel_shown, activation, tile_label, page_section, tile_type, promo_text, source_images, flag, read_date`), imported with a script in chunks. Skip rows whose merchant is `UNREADABLE`. `bonus` and `minimum_spend` as given (a bare number like `20`; the page shows it with `$`). `channel_shown`: Online -> `online`, In-Store -> `in_store`, At the Pump -> `pay_at_pump`, In-Store & Online -> `in_store_and_online`, In-Store & In-App -> `in_store_and_app`, blank -> `none_shown`. Assign our own `category` as usual (`page_section` ignored).
  - `other_details` holds on-screen text only: `Tile label reads 'BONUS'` (also `NEW OFFER`, `EXCLUSIVE COUPON`), `Promo text reads "..."`, `Logo clipped`, and `Seen on the Quicksilver card view only` (the Capital One Travel banner). Every other CSV flag is dropped. Names are kept as shown (partial names like `David's`, `Carolina`, `Scott` stay partial); names differing only by capitalization use the brand's normal capitalization.
  - **Marking used:** the owner says which of their two cards they used. Set `status: used` and add `Used on <the card they name>` to `other_details` (nickname only).
  - **Refresh:** a full live re-read of the page as one CSV (`passes, seq, section, tile_kind, merchant, merchant_tld, ..., raw_text`; no offer ids, no read date), applied with `tools/refresh.py` (Capital One adapter; **Refreshing a card**): it matches, collapses repeat tiles (`N tiles listed`), pairs the mechanical leftovers, renames with the old name in `aliases` (a bare lowercase domain keeps the saved name) and proposes the doubtful pairs. Judgment that stays with the session:
    - **Doubtful pairs:** look them up on the web; a rename only if clearly the same company (Blue 70 -> blueseventy, Spacer Mobility -> The Toe Spacer, NOW (Xfinity) -> NOW, NOW -> NOW Foods, AUDIEN -> audienhearing.com and BŌTE -> boteboard.com were; Spectrum / Cox, Pink / Thomas Pink, Fever / Wig Fever, KuKirin / KuGoo, Komray Hair / Bombay Hair stayed a missing + a new offer).
    - **Category clashes:** a rename can give two cards the same merchant name with different categories, which the validator rejects. Decide the right category on the merits (the decisions file's `clashes` sets it on every card) and tell the owner. New merchants with no saved namesake get a category as usual; list the unsure ones.
- **Bank of America:** one card, `card` = `Bank of America` only (no account or last-four numbers). It stands for the owner's two Bank of America cards, which share one landing page, so there is one set of records, ids `bank-of-america/<merchant-slug>`. If the two cards' offers ever differ, tell the owner.
  - Rules: same as Capital One (every batch is a complete snapshot; at "batch complete" every `active` Bank of America offer not in the batch becomes `missing` even with no date; `used` stays `used`; `missing` deleted 30 days after `status_since`; one that reappears becomes `active`) and the same size check (batch under 70% of the previous `active` count: warn and wait; the first batch skipped it). No expiry, cap, minimum or fine print is shown: all `null`.
  - Batches arrive as a CSV (columns `offer_id, merchant, bonus, channel, icon_label, tag`), imported with a script. `offer_id` is not stored (ids come from the merchant name). `bonus` verbatim ("4% Cash back", "$10 Cash back", "Save 25%", "Save $5", "Save Now"). A bonus starting with "Save" is a discount, not cash back: the page ranks it below every reward and leaves it out of the percent / dollar / rate sorts; "Save Now" has no number and sorts last.
  - `channel`: `in-store only` -> `in_store`, `online only` -> `online`, `in-store and online` -> `in_store_and_online`.
  - `icon_label` -> `activation`: `activateBadge` -> `needs_activation`, `activatedBadge` -> `already_activated`, `autoEnrolledBadge` -> `auto_enrolled` (linked automatically, nothing to do), `shopBadge` -> `via_shop_link` (reward earned only through the "Shop now" link).
  - **Duplicates:** rows with the same merchant (compared ignoring case and repeated spaces), `bonus` and `channel` are one offer (the file has no location): `other_details` gets `N locations listed`. The first batch also had one merchant listed twice with different activation badges (Life Extension, online): kept as one offer, `needs_activation` wins, with `Listed twice: once needing activation, once auto-enrolled`. Different bonuses (or channels) at the same merchant stay separate offers with ids `-2`, `-3`, in file order. Doubled spaces in names (a dropped "&" or "-" in the export) are collapsed to one space; names differing only by capitalization use one spelling (`Lo'Roko`).
  - `tag` (`Exclusive`, `Boosted`) goes in `other_details` as `Tagged <tag>`.
  - Categories: reuse the category of any merchant already saved; in-store restaurants are `Dining` unless clearly grocery (`Tito's Market`); the rest are assigned as usual. Same-name collisions are forced to the saved category by the validator, so a different business with a clashing name gets a qualified name (the in-store `HATCH`, a downtown LA yakitori restaurant, is saved as `HATCH (yakitori restaurant)` with `aliases: ["HATCH"]`, apart from the Capital One `HATCH` in `Pets & Baby`).
  - **Marking used:** the owner says which of their two cards they used. Set `status: used` and add `Used on <the card they name>` to `other_details` (nickname only).
  - Card link is the generic `https://www.bankofamerica.com` until the owner supplies the exact deals page.
- **Citi Double Cash:** `card` = `Citi Double Cash` (nickname only; no account or last-four numbers), ids `citi-double-cash/<merchant-slug>` (a second offer with the same slug gets `-2`). Citi's Merchant Offers page keeps a separate offer list per card, chosen with a card selector, so each Citi card is its own read and its own CSV; this card's file is the Double Cash list only. If another Citi card is added, it gets its own card name, ids and batches.
  - Rules: the snapshot rule plus date-based defaults, as for U.S. Bank: every batch is a complete snapshot, so at "batch complete" every `active` Citi Double Cash offer not in the batch becomes `missing` even with no date (`used` stays `used`; `missing` deleted 30 days after `status_since`; one that reappears becomes `active`), and the size check applies (batch under 70% of the previous `active` count: warn and wait; the first batch skipped it). Card link is the generic `https://www.citi.com` until the owner supplies the exact page.
  - Batches arrive as a CSV (columns `offer_id, merchant, bonus, min_spend, max_reward_cap, channel, enrollment_state, section, expiration, promo_tag, category, source_tab, passes_seen`), imported with a script.
    - **Redeemed rows** (`source_tab` = `Redeemed`, ids `redeemed-N`) are history: skipped entirely, and nothing is marked `used` from them.
    - One row per `offer_id`. An offer in both Featured and a category section is one row (`section` `Featured;Shopping`); Featured is not a category. `promo_tag` `Featured` (or Featured in `section`) -> `other_details` `Shown in the Featured section`.
    - `bonus` verbatim (`N% Back`, `$N Back`). `enrollment_state` `Enroll in Offer` -> `needs_activation`, `Enrolled` -> `already_activated`.
    - **Expiry** is a countdown tile (`12d left`): `expires` = read date + N days (an estimate, corrected by a later batch), `expires_text` = the tile text as shown.
    - The tiles show no channel, minimum spend, cap or fine print: `channel` `none_shown` (no badge; never inferred from the id prefix), `minimum_spend`, `spend_cap`, `fine_print` `null`. Citi's `section` / `category` (Travel, Dining, Shopping...) are only a hint; assign our own `category`.
    - **Id families:** `RN-...` are restaurant offers (5% Back, names often carry a location); `RKT-...` are online shopping offers whose names are mostly bare domains; other offers have UUID ids. `offer_id` is not stored.

## Phone page
`site/index.html` (script in `site/js/app.js`) fetches `data/offers.json`. Under the search box is a wrapping row of category buttons ("All" first, then each category); tapping one lists every active offer in that category across all cards, highest bonus first, and typing narrows within it (the "Recently unavailable" group follows the same filter). Each result shows an In-store / Online / Pay at pump / In-store & online / In-store & in-app badge from `channel` (none for `none_shown`, so none on Chase). Search is a partial, case/accent/punctuation-insensitive match on merchant (plus aliases and the cuisine detail, below); word order does not matter ("table round" finds Round Table; each typed word must appear in the same name, ranked below in-order matches); same merchant on several cards sorts highest bonus first (percent/"Nx" above flat dollars, by owner's choice); tap anywhere on a row's header (name, bonus, badges) for details. A plain search shows 60 at a time with "Show more" and the count line's "(showing N, keep typing to narrow)" hint; with a card or category picked, results load 100 at a time. Offers past `expires` are hidden client-side even if still `active`.
- **Max reward:** a maximum reward stated clearly in `fine_print` ("with a $1.50 cash back maximum", "until the $50 maximum is reached", "up to $100 cash back total", "with a $50 cash back total", "up to $30 as a statement credit") shows next to the bonus ("5% cash back, max $1.50") and in the details. Parsed in the page (`maxReward()`), nothing stored. Skipped when two different amounts appear (a per-credit max plus a total: Blue Apron, Fubo, Sony) or a flat bonus already shows the same amount. 272 offers had one on 2026-10-19 (Chase and U.S. Bank only; the other cards have no fine print).
- **Details panel order:** a compact label / value list: purchase conditions first (Expires, Spending cap, Max reward, Channel, Minimum spend, Fine print), then Category, Also known as, Other details, Last read, then the cuisine and its evidence in a collapsed "Cuisine: ..." section. Card, bonus and activation are on the row, so they are not repeated (a "Recently unavailable" row shows no activation, so its details keep it). Empty fields share one muted line: "Not shown: expiry, spending cap, fine print. No other details."
- **No offers:** when bonus rows show but nothing matches, the page says "No merchant offers. Category bonuses above may apply."

- **Per-merchant "Use:" headline:** when a search matches 1 to 3 merchants (names without a " - Location" suffix; only the closest name matches when there are any; not a cuisine search), the headline shows the best total per merchant instead of the category line below. Total = what the card earns there (base rate, a standing category, or a live quarterly / Custom Cash planned rate that replaces it) + a percent merchant offer on that card. Rates and offer lists are in `site/data/cards.json` (below). Dollar offers are never added to a percent; dollar offers with no minimum stay in the rows. "Up to N%" offers never win a line on their full rate: they rank below every definite rate and get their own line, "Up to: Quicksilver 21.5% (1.5% + up to 20% Capital One offer, add to Quicksilver, online)", shown as the second line only when there is no After activating or Best deal line and it beats Ready now (Ready now then uses the card rate alone); they are left out of the "Top offer" hint. When the winning rate comes from a bonus or standing group whose keyword list says the merchant may not count (`may_not_count`: Shipt, Instacart, StubHub, Airbnb...), the line adds a short hedge, "(grocery stores, may not count for Shipt)"; the rows keep the full note. If `main` moved, it starts over on the new `main` (unrelated changes are kept); if the same record changed, nothing is saved and the bar says what it is now, with Retry. The CSP is unchanged (the worker falls under `script-src 'self'`). **When a page file or data file is added or removed, update `CODE` / `DATA` in `sw.js` and `CODE` in `copy.js` (and `DATA_FILES` in `app.js` for data); a change to the cache names in `sw.js` (`PREFIX`, `VERSION`, `CURRENT_KEY`) needs the same change in `copy.js` (`META`, `CURRENT`).**

On every open, and when the page comes back on screen (at most once per 30 s), the worker reads it (no HTTP cache); a different commit downloads the set into a staging copy (a file whose hash matches the saved one is reused with no request; the rest by conditional request), requires every file to be 200/304, parse as JSON and match its hash, reads `version.json` again (changed: discard, retry next check), and only then replaces the copy as a whole set. A failed or partial download leaves the old set, so `offers.json` and `phone-edits.json` always come from one deploy (a fold rewrites one and empties the other). Only a 404 counts as no `version.json` (local tests: every file revalidated, still replaced only as a whole set); any other error or a broken stamp fails the check and keeps the copy. A newer `sw.js` is picked up on each page load and, for a tab that only comes back on screen, by `registration.update()` once a check and its swap are done. Swaps read the new set straight from Cache Storage (`CardCopy.readSet`, the layout `sw.js` writes), never through the worker: reads through the old worker while a new one installed hung every later open in Chromium.

New page code reloads the page the next time it comes back on screen, only when nothing would be lost: empty search box (any typed character counts), no save running or save bar showing (the small "Live" pill aside), no category, card, cuisine or Used filter, no open details, Filters panel, bonus strip or Edit mode panel, no form field in use (the empty search box counts as idle even while focused, since it is autofocused on every open). A swap rebuilds only what its changed files touch (an unchanged bonus file keeps the strip as it is). When a check can't reach the site, a grey line under the count line says "Offline · saved copy from Oct 20, 3:12 pm" until a check gets through.

On every load and swap, after `phone-edits.json`: the record shows "after" -> dropped; "before" -> "after" put back on the page's copy; anything else or gone -> dropped; also dropped after 24 hours and on a conflicting save of that record. Display only: store.js never sees it (it stays the only file that knows about GitHub).
  - **Refused save ("reload"):** the page runs a full check at once; if it brings a newer `offers.json`, it swaps it in and retries the save once; otherwise the existing message shows. Offline saves fail with the existing "Couldn’t reach GitHub" message (no queue).
  - **Off switch:** set `var ON = false;` at the top of `site/sw.js`, then commit, open the pull request into `main` and merge. The phone's next open (a page load, or the tab coming back on screen and its check) is still served from the old copy and installs the new worker, which deletes the saved copy and unregisters itself; from the next page load the page comes from the network as before (the page still registers `sw.js`, which removes itself again at once). Set it back to `true` to turn the copy on again.
  - **Tests:** `node tools/offline_test.js` (phone width, worker on, a Pages-like local server with ETags and a test `version.json`, a mock GitHub API; runs with the sort checks). `tools/sort_test.js` and `tools/phone_edits_test.js` run with service workers blocked so their request interception works.

## Publishing
- **No personal information about the owner** (name, email, phone, address, card or account numbers) goes in the repo, its commit messages or PR text. The repo is public.
- `main` is the default branch. The live site (https://cc.assyrian.co/) deploys **only from `main`**, via `.github/workflows/pages.yml` (runs `python3 tools/validate.py`, stamps `site/version.json` with `tools/write_version.py`, then publishes only `site/`; Pages source is "GitHub Actions"). `main` has no branch protection or rulesets (checked 2026-10-19), which phone edits rely on: adding a rule that requires pull requests would block them.
- Work on the branch the session starts on. Changes there go live **only after merging into `main`**, so after each batch or change: commit, push, open a pull request into `main`, and merge it; if you can't merge, tell the owner to. Say which it was.
- If that branch's PR is already merged, restart the branch from the latest `main` (same name) before new work.
- The **Fold phone edits** workflow also commits to `main` (with its own token, which doesn't start `pages.yml`) and deploys itself in the same `pages` concurrency group.
- A data-only change must still touch `site/**` (it does: `offers.json`) for the deploy to run.
